## Situation in one paragraph

Project 1 built a passive JA3/JA3S/JA4 fingerprinting tool in Python
(`src/tls_fingerprint/`, 61 tests, five measured clients). It is correct on the
fingerprint arithmetic but was graded down for (a) documented results that no
longer reproduce from the committed captures, (b) a spoofing detector that
flags genuine Chrome, and (c) a single-commit, single-author history that gave
no evidence of four people working. Project 2 is **not** an extension of that
code. It is a measurement study: document the fingerprint landscape field by
field, find 7 practical limitations each backed by a captured packet, then go
deep on two of them and produce one fix or a precise statement of what a fix
would require.

## The direction, as the professor gave it

Do not implement from scratch. Take the existing implementations (FoxIO JA4+,
tshark, ja4db) as black boxes, find where they fail, trace each failure to the
RFC section that causes it, and then solve one or two. His words: *"the first
step is getting the limitation… you would want to say, at least you are on 1 or
2 of them. That would be a meaningful conclusion."* On scope: *"If I have to give
you an objective, I would say, do QUIC. That's a challenge I'm not expecting that
he will solve it."*

## Hard constraints

1. Every limitation needs a committed capture and a command that reproduces the
   number. A claim without a capture does not go in the report.
2. Every field needs an RFC **section** citation, not just the RFC number.
3. Every printed number is regenerated by `make eval` from the committed corpus
   — never typed by hand. (This is the defect that cost marks in Project 1.)
4. Four authors visible in the git history, raw timestamped AI logs committed
   alongside the code in the same PR, and a human-written `DECISIONS.md`.
5. `pytest`-green on a clean clone, on a machine that is not the author's.
